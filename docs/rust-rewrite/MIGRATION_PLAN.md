# Migration and implementation plan

The Rust application is isolated in `rust/`. Keep Kotlin/Compose and Gradle builds usable until the parity ledger is closed.

1. **Foundation (this branch's first milestone).** Compile a Slint window from Rust, load a repository asset, implement typed route state and a theme toggle, and add tests for pure state. Validate Linux compilation; Windows compilation and GUI inspection require their environments.
2. **Visual parity.** Port measured screen geometry, SF Pro Display assets, icon paths, typography, hover/focus, player chrome, backgrounds, scrolling, and scale behavior. Capture paired screenshots of Kotlin and Rust at 1220 × 780 and 900 × 600, at supported scales. Experiment with native blur, Canvas, and animated lyrics; record frame time and memory before picking GPU rendering.
3. **Playback and data.** Implement queue/state separately from decoding; compare FFmpeg-backed decode, source resolution, audio output, seeking, transitions, and error recovery on identical media. Run long-play and repeated-switch tests. Do not change the Kotlin engine.
4. **Services and accounts.** Port shared YouTube Music/Spotify semantics carefully. Audit the existing browser-based login and PoToken flows before choosing a Rust-compatible embedded auth component. Never collect credentials in test logs. Test anonymous, active, expired, switched, and reconnected sessions.
5. **User data migration.** `DesktopPersistence.kt` uses Java `Preferences.userRoot().node("com.music.bitchord.desktop")`; `DesktopListeningStats.kt` uses `.desktop.stats`. `DesktopPreferenceChunks.kt` chunks larger values. `DesktopAccounts.kt` saves account metadata under versioned preference keys and tries Secret Service for YouTube cookies, falling back to a preference value if the keyring is unavailable. `DesktopSpotifyCanvas.kt::DesktopSpotifyToken` also stores the Spotify cookie in preferences. Windows source configuration may be DPAPI-protected. Downloads live under the user's `Music/BitChord` folder (`DesktopDownloadManager.kt`), and media cache uses `DesktopMediaCache.kt`.

   The Rust foundation reads **none** of these stores. First create fixture exports with synthetic accounts and playlists, then build a read-only parser and compatibility tests for Windows registry/Java preferences, Linux Java preferences, preference chunks, path normalization, and protected secrets. Treat preference exports as sensitive because they can contain session cookies; never attach raw exports to CI or logs. Do not promise credential reuse until platform tests pass. Import into a separately versioned Rust store using temporary files, fsync, and atomic rename, preserving a backup and the original store. Keep the Kotlin fallback readable. No automatic import or deletion should occur before these tests pass.
6. **Integrations and packaging.** Add MPRIS/SMTC, tray, media keys, Discord, scrobbling, listen together, then reproducible Windows and Linux artifacts without altering existing Kotlin workflows. Publish a migration build only after documented feature, visual, stability, and data checks.

Do not mark the draft PR ready for merge until independent Rust playback/authentication, Windows/Linux GUI runs, migration recovery, and measured performance are verified. Each stage should land in a small compileable commit with the remaining gaps kept in `FEATURE_PARITY.md`.
